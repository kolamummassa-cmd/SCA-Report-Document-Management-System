## 1. Introduction

### 1.1 Purpose
This document specifies the requirements for the **SCA Report & Document Management System**, a secure, central digital platform for Stop Child Abuse (SCA) to create, approve, store, search, and archive all organizational reports and documents. It is intended for the project sponsor, technical team, and future maintainers as the authoritative reference for scope and behavior.

### 1.2 Organization Context
SCA (operating name **VASTARE** in some jurisdictions) is a refugee-led non-profit dedicated to eradicating child abuse and gender-based violence (GBV) through community-led protection, sustainable-energy innovation, and inclusive education.

- **Tagline:** "Heal. Protect. Restore."
- **Mission focus:** Every child has the right to live free from violence, exploitation, and abuse.
- **Core programme areas:** Child Protection; the Convention on the Rights of the Child (CRC) advocacy; Early Childhood Development; Child Nutrition; Adolescent Development & Participation; Advocacy.
- **Geography:** Kenya (Kakuma Refugee Camp, Turkana County) and the Democratic Republic of Congo (Uvira, South Kivu).
- **Legal status:** Registered in Kenya as "Stop Child Abuse Community Based Organization" (Community Groups Registration Act No. 30 of 2022); registered in DRC as "Child Abuse in Congo/VASTARE" (ASBL).
- **Contact:** info@sca.or.ke

These facts inform the Organization Profile module, seed data, and branding, and should be confirmed with SCA staff before go-live.

### 1.3 Scope
The system is simultaneously:

1. A **Report Management System** — creation, submission, and multi-level approval of Daily, Weekly, Monthly, Quarterly, and Annual reports, plus specialized report types (Project, Programme, Donor, M&E, Finance, Training, Incident, Emergency).
2. A **Document Management System (DMS)** — centralized, versioned repository for all organizational files (policies, manuals, research, proposals, success stories, media).
3. A **Digital Archive** — permanent, auditable, backed-up storage of record.
4. A **Knowledge Repository** — searchable, tagged, categorized content discoverable across the organization.
5. A **Central Database** — the system of record for programmes, projects, departments, users, and their relationships.

Out of scope for v1: public-facing donor portal, mobile native apps (responsive web only), and integration with SCA's public website (www.sca.or.ke) or its CMS.

## 2. Overall Description

### 2.1 Product Perspective
A new, standalone, self-hosted web application. Next.js/React frontend, Node.js/Express API, PostgreSQL via Prisma ORM. File storage is local disk in development and AWS S3 or Cloudflare R2 in production. It does not depend on any existing SCA system.

### 2.2 User Classes and Characteristics

| Role | Summary | Technical proficiency assumed |
|---|---|---|
| Super Administrator | Full system control: users, roles, permissions, settings, backups | Medium–High |
| Executive Director (ED) | Org-wide visibility, final approvals, analytics | Low–Medium |
| Programme Manager | Manages programmes, approves reports, monitors staff | Low–Medium |
| Project Officer | Submits/edits reports, uploads documents, tracks projects | Low |
| Monitoring & Evaluation Officer | Statistics, dashboards, exports, performance analysis | Medium |
| Finance Officer | Finance documents/reports, finance analytics | Low–Medium |
| Human Resource Officer | HR documents, staff records | Low–Medium |
| Staff | Submits own reports, uploads files, views own history | Low |

Detailed capability matrix in Section 5 (Permission Matrix).

### 2.3 Operating Environment
- Server: Linux (Docker containers), Node.js 20+ LTS
- Database: PostgreSQL 15+
- Browser support: latest 2 versions of Chrome, Edge, Firefox, Safari; responsive down to 375px width
- Object storage: local filesystem (dev), S3-compatible (Cloudflare R2 preferred for cost, AWS S3 as alternative) in production

### 2.4 Design and Implementation Constraints
- Must use the specified stack (Next.js, TypeScript, Tailwind, shadcn/ui, Express, Prisma, PostgreSQL — see Architecture doc).
- Must run in Docker for consistent deployment.
- File uploads must be validated by content, not just extension (MIME sniffing + extension allow-list).
- Configurable maximum upload size (env-driven, default 100 MB per file, admin-adjustable).
- Must support child-safeguarding data sensitivity: any document/report referencing a minor's identity must be access-restricted by default (see Section 6.7).

### 2.5 Assumptions and Dependencies
- SCA will provide final logo files, brand color approval, and legal organization details prior to Phase 2 seed-data population.
- Email delivery via a transactional provider (e.g., SMTP relay, Postmark, or SES) to be selected in Phase 2.
- Internet connectivity at field offices may be intermittent; UI should tolerate slow connections (optimistic UI, retry-safe uploads) — offline-first is out of scope for v1.

## 3. Functional Requirements

### 3.1 Authentication & Account Management
- FR-1.1 Users log in with email + password.
- FR-1.2 Forgot password sends a time-limited, single-use reset link by email.
- FR-1.3 Reset password enforces password policy (min 12 chars, mixed case, number, symbol).
- FR-1.4 New accounts require email verification before first login.
- FR-1.5 Authentication issues a short-lived JWT access token (15 min) and a long-lived refresh token (7–30 days, rotated on use, stored as httpOnly secure cookie).
- FR-1.6 Sessions are revocable individually (per device) by the user or an administrator.
- FR-1.7 Account lockout after 5 consecutive failed attempts within 15 minutes; unlock via admin or timed cooldown.
- FR-1.8 Passwords are hashed with bcrypt/argon2; never stored or logged in plaintext.
- FR-1.9 All authenticated actions are authorized via RBAC middleware (see Section 5).

### 3.2 Report Module
- FR-2.1 Users with report-creation permission can create a report of any enabled Report Type (Daily, Weekly, Monthly, Quarterly, Annual, Project, Programme, Donor, Monitoring, Evaluation, Finance, Training, Incident, Emergency).
- FR-2.2 Every report captures, at minimum: report number (auto-generated, unique, human-readable e.g. `SCA-RPT-2026-000123`), title, type, programme, project, department, reporting period (start/end), date, location (country/county/sub-county/ward), prepared-by, supervisor, executive summary, objectives, activities conducted, achievements, challenges, lessons learned, recommendations, next steps, beneficiary breakdown (male/female/children/adults/PWD), budget (allocated/used/remaining), attached photos/videos/supporting documents, optional GPS coordinates, digital signature, status, and comments.
- FR-2.3 Report status lifecycle: `Draft → Submitted → (Approved | Rejected → revision → Submitted)`. Every transition is timestamped and attributed.
- FR-2.4 Full revision history is retained (immutable snapshots per submission), viewable as a diff/timeline.
- FR-2.5 Approval workflow is configurable per report type (e.g., Project Officer → Programme Manager → Executive Director) with support for single- or multi-step approval chains.
- FR-2.6 Reports can be commented on by users with view/approve permission; comments are threaded and timestamped.
- FR-2.7 Reports are exportable as PDF, Word, Excel, and CSV (tabular fields); generated files include SCA logo, organization header/footer, page numbers, generation date, prepared-by/approved-by, digital signature, and report number.
- FR-2.8 Bulk export of a filtered report set as ZIP.

### 3.3 Document Management System
- FR-3.1 Upload any of: PDF, DOC/DOCX, XLS/XLSX, CSV, PPT/PPTX, common image formats, common video formats, ZIP.
- FR-3.2 Every document is categorized by year, programme, project, department, country, region, county, location, author, document type, tags, and freeform keywords.
- FR-3.3 In-browser preview for PDF, images, and Office formats (via rendered preview, not just download).
- FR-3.4 Version history: uploading a new version of an existing document preserves prior versions with uploader, timestamp, and change note; any version can be restored or downloaded.
- FR-3.5 Per-document comments and an immutable audit history (view, download, edit, share events).
- FR-3.6 Per-document and per-folder sharing/permission overrides layered on top of role defaults.
- FR-3.7 Soft-delete with restore window before permanent deletion; permanent deletion requires elevated permission and is itself audit-logged.

### 3.4 Search
- FR-4.1 Global search bar available from every authenticated screen.
- FR-4.2 Search and filter by: title, keywords/tags, programme, project, department, location, author, year, date range, report type, document type, status, file type.
- FR-4.3 Search returns results within 500ms for typical result sets (target; see Non-Functional Requirements) using database full-text search/indexing (e.g., PostgreSQL `tsvector` or equivalent).
- FR-4.4 Search results are permission-filtered — users never see results they are not authorized to view.

### 3.5 Dashboard & Analytics
- FR-5.1 Role-aware dashboard with summary cards: total reports, reports submitted today, weekly/monthly/quarterly/annual report counts, pending/approved/rejected counts, active projects, active programmes, total users, total files, storage used.
- FR-5.2 Interactive charts: monthly/quarterly/yearly report volume, department performance, programme performance, project performance, staff performance, budget utilization, beneficiary statistics, geographical distribution.
- FR-5.3 Charts support drill-down (click a segment to filter the underlying report/document list) and date-range selection.
- FR-5.4 Analytics data is exportable (image/CSV) for use in donor reporting.

### 3.6 Calendar
- FR-6.1 Calendar view showing upcoming report deadlines (derived from report-type cadence), completed reports, meetings, and organizational events.
- FR-6.2 Deadline reminders configurable per report type/cadence (weekly, monthly, quarterly, annual).

### 3.7 Notifications
- FR-7.1 Email notifications for: report approval, report rejection, upcoming deadlines, and weekly/monthly/quarterly/annual reminders.
- FR-7.2 In-app notification center with read/unread state and deep-links to the relevant report/document.

### 3.8 Audit Log
- FR-8.1 Every login, logout, create, update, delete, approve, reject, download, view, file upload, and settings change is recorded with actor, timestamp, IP, entity type/ID, and before/after state where applicable.
- FR-8.2 Audit log is append-only, filterable, and exportable by Super Administrator and Executive Director.

### 3.9 Settings & Administration
- FR-9.1 Organization profile management: logo, mission, vision, contact details, registration details.
- FR-9.2 CRUD for departments, programmes, projects, roles, permissions, users.
- FR-9.3 Storage configuration (provider, quota, max upload size).
- FR-9.4 Backup configuration and manual trigger; restore workflow for database and documents.
- FR-9.5 Email/SMTP configuration.
- FR-9.6 System preferences (date format, timezone, default language, session timeout).

### 3.10 Backups
- FR-10.1 Automatic daily, weekly, and monthly backups of database and document storage.
- FR-10.2 Backup retention policy configurable; oldest backups pruned automatically.
- FR-10.3 Restore workflow tested and documented (see Deployment Guide, Phase 5).

## 4. Non-Functional Requirements

| Category | Requirement |
|---|---|
| Performance | Search results < 500ms typical; page loads < 2s on broadband; file preview < 3s for files ≤ 25MB |
| Availability | Target 99.5% uptime for production; graceful degradation if storage provider is briefly unreachable |
| Scalability | Horizontally scalable API (stateless, JWT-based); database indexed for 100k+ reports and 500k+ documents without redesign |
| Security | See Section 6 |
| Usability | WCAG 2.1 AA accessibility target; responsive desktop-first, tablet- and mobile-friendly; dark/light mode |
| Maintainability | Feature-based architecture, typed end-to-end (TypeScript), documented API, automated tests on critical paths |
| Localization | English by default; UI text externalized to support future translation (e.g., Swahili, French for DRC operations) |
| Auditability | Every state-changing action traceable to a user, timestamp, and IP |
| Data retention | Reports and documents retained indefinitely by default (archival mandate); deletion is soft by default and permission-gated |

## 6. Security Requirements

1. **6.1** JWT access + rotating refresh tokens; refresh tokens stored httpOnly, secure, sameSite.
2. **6.2** Passwords hashed with bcrypt (cost ≥ 12) or argon2id.
3. **6.3** All inputs validated server-side with Zod schemas; no trust in client-side validation alone.
4. **6.4** Rate limiting on auth and search endpoints; progressive backoff on repeated failures.
5. **6.5** Helmet-equivalent HTTP security headers; strict CORS allow-list; CSRF protection on state-changing cookie-authenticated routes.
6. **6.6** Parameterized queries via Prisma eliminate SQL injection; output encoding/sanitization prevents XSS; file uploads scanned by MIME + magic-byte validation, stored outside the web root with randomized keys.
7. **6.7** Child-safeguarding data handling: reports/documents identifying a minor by name or image are flagged sensitive and restricted to roles with explicit "sensitive data" permission; audit log entries for sensitive records are retained at the same sensitivity level.
8. **6.8** All administrative and destructive actions require re-authentication or step-up confirmation for high-risk operations (e.g., permanent delete, role changes).
9. **6.9** Full audit logging (Section 3.8) covering authentication and data access, not just mutations.
